# 2026-07-08 · FM Radio — Port del stock MT6627 (en curso)

## TL;DR — ESTADO ACTUAL
El stock FM completo (12.304 LOC) **compila y se linkea al vmlinux** de mainline 7.0.12.
El último boot flasheado (`boot-fm-linked.img`, md5 `5a5403a2...`) incluye el FM por primera vez.
**Falta verificar**: hacer power-cycle físico y comprobar si `/dev/fm` aparece y responde a POWERUP/TUNE.

## Lo que se ha hecho (sesión 0708)

### 1. Investigación (3 agentes en paralelo) — commit `0fcf5f4`
Ver `mainline/CAMARA-MODEM-FM-INVESTIGACION-0707.md`. Resumen:
- Cámara = NO-GO (HAL cerrada imprescindible, kernel es passthrough tonto)
- Módem M1 (arrancar baseband) = GO (kernel-autocontenido, playbook WiFi)
- FM = CONDITIONAL GO (~12K LOC no 29K, reusa CONSYS, no hay HAL cerrado)

### 2. M0 — Test de transporte validado en HW
Módulo `mt6582_fm_test.c` (debugfs) que hace `func_on(FM)` + envía POWERUP por STP canal 1.
**Resultado en HW**: `func_on(FM) OK` + `POWERUP enviado (9 bytes)`. El CONSYS levanta el FM
y el canal STP-1 transmite. ✅

### 3. btif extendido con canal FM — `mt6582-btif.c`
Añadido al btif (que YA funciona para BT/GPS/WiFi):
- `#define STP_TYPE_FM 1` (junto a BT=0, GPS=2, WMT=4)
- Campo `fm_rx_cb` + `fm_cb_lock` en la struct
- Routing en `rx_thread`: frames canal 1 → invoca `fm_rx_cb`
- Funciones exportadas: `mt6582_stp_fm_send()` (TX) + `mt6582_stp_fm_register_rx()` (RX callback)
- Compila limpio ✅

### 4. Shim/glue — `fm_glue.c` + headers
Implementa las APIs externas que el stock espera:
- `mtk_wcn_stp_send_data/receive_data/register_event_cb` → canal STP-1 del btif
- `mtk_wcn_wmt_func_on/off/chipid_query/hwver_get/msgcb_reg` → consys_func_on/off
- `mtk_wcn_cmb_stub_audio_ctrl` → no-op (audio es HW analógico)
- kfifo de RX: el stock drena con `receive_data`, el btif encola con el callback
- Headers shim: `stp_exp_shim.h`, `wmt_exp_shim.h`, `mtk_wcn_cmb_stub_shim.h`
  (definen tipos UINT8/UINT32/INT32/MTK_WCN_BOOL que `fm_typedef.h` no tiene)

### 5. Stock copiado + fixes fricción 3.10→7.0
Stock en `drivers/misc/mediatek/fmradio/` (core/ 8 ficheros + mt6627/pub/ 4 ficheros + inc/ headers).
Fixes aplicados al `fm_module.c` y otros:

## Cómo seguir (en la otra sesión)

### Paso 1: Power-cycle físico + verificar /dev/fm
El último flasheado es `boot-fm-linked.img` (md5 `5a5403a2...`, sector 83968).
Hacer **power-cycle físico** (NO sysrq — deja el PMIC mal). Tras arrancar:
```sh
ssh root@<ip-movil> "ls -la /dev/fm* ; dmesg | grep -iE 'fm|6627' | tail -15"
```
Si `/dev/fm` existe y hay mensajes del FM en dmesg → el driver cargó ✅

### Paso 2: Si NO aparece /dev/fm
Posibles causas:
- `fm_env_setup()` falla (busca ficheros de configuración del FM)
- `platform_device_register` o `platform_driver_register` falla
- El `fm_mod_init` (que llama `mt_fm_init`) no se ejecuta
Debug: el `mt_fm_init` tiene un `pr_info("mtk_fm_drv: mt_fm_init entered")`.
Buscar en dmesg: `dmesg | grep mtk_fm_drv`. Si no aparece → el initcall no corre.

### Paso 3: Si /dev/fm aparece — probar POWERUP/TUNE
El stock expone 53 ioctls MTK (magic 0xf5). App mínima de test en C:
```c
int fd = open("/dev/fm", O_RDWR);
unsigned long arg = 0;
ioctl(fd, FM_IOCTL_POWERUP, &arg);   // encender radio
// FM_IOCTL_TUNE para sintonizar una frecuencia
```
Los defines de ioctls están en `fm_ioctl.h` del stock.

### Paso 4: Si POWERUP funciona — probar TUNE + audio
- TUNE a 98.0 MHz (o la frecuencia local)
- El audio del FM va por path analógico al auricular (no I2S SW)
- Necesita auriculares enchufados (antena)

## Lecciones de esta sesión
- **sysrq reboots dejan el PMIC mal** (0 IRQs del powerkey). Power-cycle físico siempre.
- **`pwrap_poke` desde userspace no es fiable** para registros que cambian rápido (caché del pwrap).
- **El "obj-y += directorio/" debe estar en el Makefile padre** o el código no se linkea al vmlinux
  aunque compile por separado con `M=`. Esto nos costó una iteración.
